### 2.9 `uvk1_gb2312_font.bin` 的独立判断（对应任务 9）

**报告的说法**：`327568 = 2944 + 6763 × 48`，头部 2,944 B + 6763 个 24×16 字形（48 B/字），非零密度 ~0.31。

**我的实测**：

| 观测 | 数值 | 与"2944 + 6763×48"是否相容 |
|---|---|---|
| 文件大小 | 327,568 = 16 × **20,473**（严格整除） | 只是算术巧合；327568/48 = 6824.33，不整除 |
| 统计量的周期 | 全文件按 **16 字节**分组后，"每记录第 p 字节的非零率"严格以 16 为周期（p=0..15 的曲线在 3 个 16 B 块里完全相同） | ✗ 48 B 单元内部应出现"3 行一组"的扫描线结构，实测是 16 B 一组 |
| 每记录末字节 | 20,473 条中 **20,449** 条第 16 字节为 0（只有 32 个 bit 被置位） | ✗ 24×16 位图的第 3 列字节不可能恒为 0 |
| 是否有 2944 处断点 | **没有**：0..2944 与 2944.. 的统计完全同构；2944 = 184×16，只是 16 B 单元的整数倍 | ✗ 无任何"头部结束"的特征 |
| 声称字形区的中段 | foff **0x067DE–0x0B042 = 18,532 B 连续全零**（1163 个 16 B 单元） | ✗ GB2312 一级汉字是连续的 3755 字，不存在 1100+ 个连续空白字形 |
| 墨密度 | 全文件 bit 密度 **0.2212**（579,671 / 2,620,544）；正文段 **0.2227**；按"非零字节"算是 **0.6001** | ✗ 报告的 ~0.31 与两种口径都对不上 |
| 分区墨密度 | foff 0x00000–0x67DE ≈ 10/128 px；0x0B042–0x3FE3D ≈ 26/128；**0x42C10 之后 45–60/128** | ✗ 单一字模不该有这种 6 倍落差；末段墨密度已接近"图形"而非"文字" |
| 行宽检测（相邻行 Jaccard） | W=8 峰值 0.328，W=16 次之 0.264，其余 ≤0.13 | 支持"行 = 1 字节（8 px）"，不支持 24 px/行 |
| 三元组相关性 | 按 3 记录一组，"组内 vs 跨组 vs 随机"的行占用 Jaccard 分别是 0.610 / 0.606 / 0.588（几乎无差别） | ✗ 若 3 条记录拼成一个字，组内相关性应显著高于跨组 |

**我的结论**：
1. **算术分解成立但结构证据全部相反**。文件更可能是 **20,473 个 16 字节单元**的序列（16 B/单元：8 px 宽 × 16 行，单元内第 16 字节恒为 0 作占位），而不是"2944 B 头 + 48 B/字形"。
2. 即使退一步接受"每字 3 单元、24 px 宽"，也与"组内相关性 = 跨组相关性"这一实测冲突。
3. 末段（0x42C10 以后）墨密度 35%–47%，不可能是文字点阵，更像位图/图形资源；**该文件很可能是"字模 + 图形资源"的混合包，或根本是另一个格式**（例如 8×16 单字节字模表覆盖了某种私有编码）。
4. 要下定论，必须看**消费该文件的固件加载代码**（uvk1 侧），这份材料里没有；仅凭文件本身只能给出"报告的结构模型未被证实、且有多条反证"。

> 建议报告改成：「`uvk1_gb2312_font.bin` 的确切结构**未确认**。已知：大小 327,568 = 16×20,473，全文件呈严格 16 字节单元结构（每单元 16 B，末字节恒 0），墨密度 0.22，中段有 18,532 B 连续空白，末段墨密度异常高。`2944 + 6763×48` 只是算术上成立，**不能作为结构结论**；`6763` 这个数来自 GB2312 汉字数，属于"倒推"，不是从文件里读出来的。」

## 4. 结论

1. **报告的核心安全结论（PIN/UID 派生、AUTH 记录、RDP 加锁、基址 0x08002800）全部成立**，恢复出的算法与二进制逐条吻合，这点很难得。
2. **错误集中在"地址/数值的搬运"上**：基址更正只改了 §9，§1/§3.1/§4/§6 留着旧视图址；3 处表地址错 0x800（0x0800A304）、0x24（0x0800A2BC→0x0800A2E0）、以及影子寄存器数量/范围；1 处字节序（"AUTH"→"HTUA"）；1 处尺寸（12×16→12×12）。
3. **两处结论性错误**必须改：§4 的"VTOR 异常/反分析痕迹"，§12.10 的"mangosteen 是落在数据表的镜像"。两者成因相同 —— 都是把 `0x08002800` 当成了旧视图址。
4. **bootloader 章节（§12.13/§12.14）质量最高**：帧格式、横幅 14 字节、0x0518 结构、三条命令与三条应答、256 B 页擦、472 页、跳转判据、PC13 手电筒、38400 8N1、UID 4 word、双 2048 B ring —— 全部核对通过；只有 PTT 判据的 GPIO 端口/掩码是错的。
5. **`uvk1_gb2312_font.bin` 的结构结论应当撤回**，改为"未确认"，因为所有结构性统计都与"2944 + 6763×48"不符。
